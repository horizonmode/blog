# The Background

Microsoft Fabric is a new Unified Data Platform in the Analytics space, designed at a high level
to bring together Data Science, Data Engineering and Analytics workloads in a single platform. 
They've also added some Transactional Database support with standard PaaS Microsoft SQLServer also 
on the same platform. 

As a product it supercedes Microsoft Synapse Analytics which was delivered and accessed through Azure. A Key
difference here being Synapse was PaaS, and Fabric is better described as SaaS, 
although some configuration, maintenance and monitoring are still required. 

After one year of rolling this platform out at an enterprise level, I have identified some clear wins, 
and we have also experienced some significant challenges:

## Wins

### Accessibility and Wide Adoption 

Because it's a SaaS product and includes many low-code options for getting started, 
the platform is being used by a wide range of users outside of the technology area. 
Some of these are Data Scientists and Engineers, but many are non-technical. Fabric seems
to have a low barrier to entry, whilst also being able to scale-up 
if required. For instance, users have quickly brought in data from Sharepoint Lists 
into a workspace and created reports, replacing what was previously done in Excel. 

### Deployment Flexibility

Developers and Engineers are able to connect to GitHub or Azure DevOps in 
differnet modes, and migrate changes across workspaces using Source Control or Fabric Deployment Pipelines.
However this is optional, and business users can instead choose to have a single workspace
and use native tools to manage versioning. Versioning mechanisms
are different per Fabric item type, but Notebooks for example have rollback and editing history built-in.

### Easy Ingestion

The value customers get out of the platform is positively correlated with the 
number of data sources on-boarded, and as such Microsoft have made this flexible. 
If sources are within the Microsoft eco-system it's often possible to set up
shortcuts or mirroring which are the easiest option. If not, you have 
a range of low-code (Copy Jobs, Dataflow Gen 2) and Pro-code (Notebooks) options
to perform periodic ingestion. There is also a separate path for ingesting
events with the real-time stack.

### Power BI

If you are already using Power BI, Fabric extends the same tools and portal experience. There 
is also wide support of Fabric data sources within Power BI Desktop and the Power BI Web experience. 
Semantic Models are used as the modelling layer for reports, and these can be edited and created
independently within a Fabric workspace. Also, see challenges on this. 

### Reverse ETL and Translytical

We've had some success with User-Defined functions in Fabric, which allow you 
to have lightweight trnsactional workflows embedded into Power BI Reports. 
This has meant we have not needed to create an entirely separate application 
where there is a marginal transactional requirement. This also works well 
when the Power BI Reports are in the same Fabric workspace as the data it references, 
with Power BI Apps providing the publish mechanism for the entire solution.

### Lakehouses

A common starting point for all users is the lakehouse, providing 
the ability to upload, ingest and store data in it's raw form, 
then generate delta parquet tables to use for analysis and reporting.
This has proved accessible for all types of users. The lakehouse also provides a SQL Endpoint to query data. 
The lakehouse also comes in Data Warehouse flavour if the skill-set
of users is closer aligned to Microsoft SQLServer Data Warehouse.

## Challenges

### Costs and Capacity Model

Fabric has a capacity based [cost model](https://learn.microsoft.com/en-us/fabric/enterprise/licenses), which is clear enough. However
this can get complex when you have a diverse user base from different departments, roles and disciplines all 
sharing the same platform, alongside managed products and reports published and managed centrally. 
The challenge is in finding a model which satisfies these conditions: 

- Allowing seperation of workload between business critical resources, and user-defined reporting. 
- Allowing costs to be reported to a department or project across workloads. 
- Grouping workload types together to enable scaling.
- Avoiding under-utlised capacities.
- Being easy to maintain by Fabric Admins.

### Workspace Standards

Similarly, workspace administration has similar challenges. We ended up having naming convention which 
included Domains, workspace type (personal, team-productivity or application) and optional 
features such as environment. Linking these to the Domain Model managed in the Power BI / Fabric tenant
was also initially helpful but required alignment across the organisation.

### Tenant Settings 

Tenant Settings were difficult to get right. Examples of these were: 

- Semantic Model editing permissions making it impossible for users to create any Power BI Reports in the portal
- XLMA permissions for live Excel based reporting stopping Excel connections
- Direct Query connections disabled by default
- Users couldn't create Fabric items by default despite having access to a Fabric-linked workspace

### Deployment Pipelines

The built-in Fabric Deployment Pipelines are an easy out-the-box
solution to enable moving items between workspaces. However, some limitations were identified relating to variables
and connections, meaning we ended up with a list of post-deployment manual steps not limited to: 

- Changing sources and destinations on activities
- Changing ownership of items
- Connection strings both within and external to Fabric
- Labels and user-facing text

### Connection Management

This was a steep learning curve. Connections are first-class objects in Fabric and can be managed from 
a dedicated admin area. One limitation is that if one user creates a connection, another user 
cannot use it by default unless it's explictitly shared. This also applies to trying 
to use the connection in a Deployment Pipeline. Even administrators cannot access
a connection if it isn't shared with them.

In the end, we attempted to find the fewest connections needed for each solution and share them between environments. 
Using an Entra group for anyone needing developer access to a workspace also helped with sharing.

### Sharing Model

Adding users to a workspace is trivial but we experienced challenges when considering 
how best to share Power BI Reports and Dashboards. Power BI Apps are used where possible but 
we wanted Apps to remain focused on corporate use-cases. For end users trying to share a custom dashboard 
outside of their time, this seemed overkill. We are currently exploring Org Apps for this, or whether to allow
workspace contributors the ability to directly share their reports and dashboards without an app.
