# The Background

[Microsoft Fabric](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview) is a unified data platform designed to bring together data science, data engineering and analytics workloads.
Microsoft has also added support for transactional databases through SQL Server on the same platform.

As a product, it supersedes Microsoft Synapse Analytics, which was delivered and accessed through Azure. A key
difference is that Synapse was PaaS, whereas Fabric is better described as SaaS,
although some configuration, maintenance and monitoring are still required.

After one year of rolling this platform out at an enterprise level, I have identified some clear wins,
and we have also experienced some significant challenges:

## Wins

### Accessibility and Wide Adoption

Because it's a SaaS product and includes many low-code options for getting started,
the platform is being used by a wide range of users outside of the technology area.
Some of these are data scientists and engineers, but many are non-technical. Fabric seems
to have a low barrier to entry, whilst also being able to scale up
if required. For instance, users have quickly brought in data from SharePoint Lists
into a workspace and created reports, replacing what was previously done in Excel.
Engineers familiar with Azure Data Factory have also found it particularly easy to transfer their skills.

### Deployment Flexibility

Developers and engineers are able to connect to GitHub or Azure DevOps in
different modes and migrate changes across workspaces using [Source Control](https://learn.microsoft.com/en-us/fabric/cicd/git-integration/intro-to-git-integration) or [Fabric Deployment Pipelines](https://learn.microsoft.com/en-us/fabric/cicd/deployment-pipelines/intro-to-deployment-pipelines).
However, this is optional, and business users can instead choose to have a single workspace
and use native tools to manage versioning. Versioning mechanisms
vary by Fabric item type, but [Notebooks](https://learn.microsoft.com/en-us/fabric/data-engineering/how-to-use-notebook), for example, have built-in rollback and editing history.

### Easy Ingestion

The value customers get out of the platform is positively correlated with the
number of data sources onboarded, so Microsoft has made ingestion flexible.
If sources are within the Microsoft ecosystem, it's often possible to set up
[shortcuts](https://learn.microsoft.com/en-us/fabric/onelake/onelake-shortcuts) or [mirroring](https://learn.microsoft.com/en-us/fabric/database/mirrored-database/overview), which are often the easiest options. If not, you have
a range of low-code ([Copy Jobs](https://learn.microsoft.com/en-us/fabric/data-factory/copy-job), [Dataflow Gen 2](https://learn.microsoft.com/en-us/fabric/data-factory/dataflows-gen2-overview)) and pro-code (notebooks) options
to perform periodic ingestion. There is also a separate path for ingesting
events with the [real-time stack](https://learn.microsoft.com/en-us/fabric/real-time-intelligence/overview).

### Power BI

If you are already using Power BI, Fabric extends the same tools and portal experience. There
is also broad support for Fabric data sources within Power BI Desktop and the Power BI web experience.
[Semantic models](https://learn.microsoft.com/en-us/power-bi/connect-data/service-datasets-understand) are used as the modelling layer for reports, and these can be edited and created
independently within a Fabric workspace. See the Tenant Settings section for the challenges we encountered.

### Reverse ETL and Translytical

We've had some success with [User-Defined Functions](https://learn.microsoft.com/en-us/fabric/data-engineering/user-data-functions/user-data-functions-overview) in Fabric, which allow you
to have lightweight transactional workflows embedded in Power BI reports.
This has meant we have not needed to create an entirely separate application
where there is a marginal transactional requirement. This also works well
when the Power BI reports are in the same Fabric workspace as the data they reference,
with [Power BI Apps](https://learn.microsoft.com/en-us/power-bi/collaborate-share/service-create-distribute-apps) providing the publishing mechanism for the entire solution.

### Lakehouses

A common starting point for all users is the [lakehouse](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-overview), which lets users
upload, ingest and store data in its raw form,
then generate Delta tables backed by Parquet for analysis and reporting.
This has proved accessible for all types of users. The lakehouse also provides a [SQL endpoint](https://learn.microsoft.com/en-us/fabric/data-warehouse/sql-analytics-endpoint-performance) to query data.
Fabric also offers a [data warehouse](https://learn.microsoft.com/en-us/fabric/data-warehouse/data-warehousing) for users whose skills are more closely aligned with Microsoft SQL Server data warehousing.

## Challenges

### Costs and Capacity Model

Fabric has a capacity-based [cost model](https://learn.microsoft.com/en-us/fabric/enterprise/licenses), which is clear enough. However,
this can get complex when you have a diverse user base from different departments, roles and disciplines all
sharing the same platform, alongside managed products and reports published and managed centrally.
The challenge is in finding a model which satisfies these conditions:

- Allowing separation of workloads between business-critical resources and user-defined reporting.
- Allowing costs to be reported to a department or project across workloads.
- Grouping workload types together to enable scaling.
- Avoiding underutilised capacities.
- Being easy to maintain by Fabric admins.

### Workspace Standards

Workspace administration presents similar challenges. We ended up with a naming convention that
included [domains](https://learn.microsoft.com/en-us/fabric/governance/domains), workspace types (personal, team productivity or application) and optional
features such as the environment. Linking these to the domain model managed in the Power BI / Fabric tenant
was also initially helpful but required alignment across the organisation.

### Tenant Settings

[Tenant settings](https://learn.microsoft.com/en-us/fabric/admin/tenant-settings-index) were difficult to get right. We ran into several issues:

- Semantic model editing permissions made it impossible for users to create any Power BI reports in the portal.
- XMLA permissions for live Excel-based reporting blocked Excel connections.
- DirectQuery connections were disabled by default.
- Users couldn't create Fabric items by default despite having access to a Fabric-linked workspace.

### Deployment Pipelines

The built-in Fabric Deployment Pipelines are an easy way to move items between workspaces. However, we found limitations with variables
and connections, so we had to complete several steps manually after deployment:

- Changing sources and destinations for activities
- Changing item ownership
- Updating connection strings both within and external to Fabric
- Updating labels and user-facing text

### Connection Management

This was a steep learning curve. [Connections are first-class objects](https://learn.microsoft.com/en-us/fabric/data-factory/connection-management-overview) in Fabric and can be managed from
a dedicated admin area. One limitation is that if one user creates a connection, another user
cannot use it by default unless it's explicitly shared. This also applies to trying
to use the connection in a deployment pipeline. Even administrators cannot access
a connection if it isn't shared with them.

In the end, we tried to minimise the number of connections needed for each solution and share them between environments.
Using an Entra group for anyone needing developer access to a workspace also helped with sharing.

### Sharing Model

Adding users to a workspace is trivial, but we experienced challenges when considering
how best to share Power BI reports and dashboards. Power BI Apps are used where possible, but
we wanted apps to remain focused on corporate use cases. For end users trying to share a custom dashboard
outside their team, this seemed like overkill. We are currently exploring [Org Apps](https://learn.microsoft.com/en-us/fabric/org-apps/overview) for this and considering whether to allow
workspace contributors the ability to directly share their reports and dashboards without an app.
